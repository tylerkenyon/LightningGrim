# LightningGrim: 26.2 movement-prediction bypass analysis

Scope: code paths gated on `ClientVersion.V_26_2` / `ServerVersion.V_26_2` in
LightningGrim at `652f7c3` (merge of upstream Grim 2.0). These are:

| Area | Files |
|---|---|
| Potent sulfur geysers | `predictionengine/blockeffects/PotentSulfurGeyser.java`, `CompensatedGeysers.java`, `events/packets/worldreader/PacketWorldReaderEighteen.java` |
| Entity bounciness / friction / air-drag attributes | `utils/nmsutil/BlockProperties.java`, `predictionengine/movementtick/MovementTicker.java`, `utils/data/packetentity/PacketEntity.java` |
| Bounce suppression tag | `MovementTicker.java#move` |
| Ground-speed formula change | `BlockProperties.getFrictionInfluencedSpeed` |
| Swim-hop + geyser | `player/GrimPlayer.java#getPossibleVelocitiesMinusKnockback` |
| Baby / sulfur-cube hitboxes, cube-mob metadata index | `utils/nmsutil/BoundingBoxSize.java`, `utils/latency/CompensatedEntities.java` |

All paths are relative to `common/src/main/java/ac/grim/grimac/`.

This only covers bypasses: movement that LightningGrim accepts but that a
vanilla 26.2 client cannot produce. Places where LightningGrim is stricter than
vanilla (false positives) are listed briefly at the end, because they are not
bypasses.

> **Confidence note.** There is no decompiled 26.2 client in this repo, so
> nothing here was checked line by line against Mojang's code. Each finding
> says what it is based on: either an internal inconsistency in Grim's own
> port (strong evidence) or an inference about vanilla (needs confirming
> against the 26.2 sources). None of the findings has been run on a live
> server yet. The reproduction steps are how to confirm them.

## Summary

| # | Finding | Requires | Severity | Confidence |
|---|---|---|---|---|
| 1 | A bouncy entity keeps its upward velocity when it hits a ceiling, so it can stick to or hover under ceilings | `bounciness` > 0 | Medium | Medium-High |
| 2 | A ground-status toggle lets a bouncy player choose any vertical velocity up to an inflated bounce, which adds energy on every bounce | `bounciness` > 0 | Medium | High (Grim-side logic) |
| 3 | `air_drag_modifier` is not applied to elytra drag, so with a modifier > 1 a player glides with less drag than vanilla allows | `air_drag_modifier` ≠ 1 + elytra | Medium | Medium (depends on vanilla) |
| 4 | Cube-mob size index 18 is used for all cube mobs on 26.2 servers. If it is wrong for any of them, the hitbox is wrong, which could mean an inflated Reach/Hitbox allowance | 26.2 server | Low–Medium | Low (verification item) |

Findings 1–3 need the player (or their vehicle) to have one of the new 26.2
physics attributes. In survival that depends on how the server grants them
(item attribute modifiers, plugins, datapacks, sulfur-cube mechanics). On a
server that never changes these attributes from their defaults
(`bounciness = 0`, `friction_modifier = 1`, `air_drag_modifier = 1`), findings
1–3 cannot be triggered.

## Shared test setup

1. Build LightningGrim (`./gradlew :bukkit:build`) and install it on a Paper
   26.2 test server with nothing else changing movement.
2. Join with a 26.2 client. You also need a test client (for example a Fabric
   dev environment with a mixin) that can change the one behaviour named in
   each finding and send the raw ground-only / position packets described.
3. Give yourself the alerts and debug views:
   `/grim alerts`, `/grim verbose`, and `/grim debug <you>`. The debug output
   shows the predicted vs actual vector and the offset for every movement.
4. Attribute IDs below are the 26.2 IDs used by packetevents'
   `Attributes.BOUNCINESS`, `FRICTION_MODIFIER` and `AIR_DRAG_MODIFIER`.
   Check the exact namespaced IDs with tab completion on `/attribute`.

"Passes" below means Simulation/Prediction offset stays under the flag
threshold and no setback happens.

## 1. Bouncy entity keeps its upward velocity when it hits a ceiling

### Where

`predictionengine/movementtick/MovementTicker.java`:

```java
// move()
if (inputVel.getY() != collide.getY()) {           // any vertical collision, floor OR ceiling
    float blockRestitution = BlockProperties.getBlockBounceRestitution(onBlock, player);
    boolean suppressesBounce = ... BlockTags.SUPPRESSES_BOUNCE.contains(onBlock);
    if (blockRestitution > 0.0F || !suppressesBounce && BlockProperties.getEntityBounciness(player) > 0.0F) {
        applyBlockBounce(blockRestitution, collide, riding);
    } else {
        player.clientVelocity.setY(0);
    }
}

private void applyBlockBounce(...) {
    ...
    double currentY = player.clientVelocity.getY();
    if (currentY >= 0.0) {
        return;                                    // <- upward velocity is left untouched
    }
    ...
}
```

### Why it is a bypass

- Without bounciness, a ceiling hit goes to the `else` branch and Y velocity is
  set to 0, which is vanilla.
- With entity `bounciness` > 0 (and not sneaking, not standing on a
  `suppresses_bounce` block), every vertical collision goes into
  `applyBlockBounce`. That method returns early when `currentY >= 0`, which is
  the case on a ceiling hit. The Y velocity is neither zeroed nor reflected, so
  Grim keeps predicting upward velocity.
- Grim's own port of the 26.2 helper,
  `BlockProperties.getVelocityAfterVerticalCollision`, handles positive
  velocity on purpose. Its only zeroing guard is
  `velocity < 0.0 && correctGravity`, and for `velocity > 0` it returns
  `(gravityCompensation - velocity) * drag * restitution`, which is a
  downward reflection. So the 26.2 bounce is meant to push a bouncy entity
  back down from a ceiling, and the early return (left over from the
  pre-26.2 slime `bounceUp`, which only acts on `y < 0`) cuts that off.
- Result: after a ceiling hit Grim expects `y ≈ (v − g)·0.98` on the next tick,
  still positive. The collision clamps the real movement to 0, so a client
  that stays pressed against the ceiling matches Grim's prediction exactly for
  several ticks. A vanilla 26.2 client would be bounced downward. This is a
  ceiling "stick" or "hover" that vanilla cannot do. Repeated jumps (or jumps
  plus finding 2) let a player hang under ceilings.

### Reproduction

1. `/attribute @s minecraft:bounciness base set 1.0`
2. Build a 2-block-high corridor: stone floor, stone ceiling at floor+2 (the
   player is 1.8 tall, so a jump hits the ceiling).
3. Vanilla baseline: jump with an unmodified 26.2 client. With `/grim debug`
   on, note that after the ceiling contact the actual Y movement goes negative
   right away (reflected).
4. Test client: hook the client's vertical-collision bounce so that when
   `deltaMovement.y > 0` on a ceiling collision the Y velocity is left as is
   (copy Grim's `applyBlockBounce` early return). Jump.
5. Expected: the client's Y position stays at `ceiling − 1.8` for about
   `v/0.08` ticks (around 4–5 ticks for a jump), then it falls. Grim's debug
   offset stays about 0 for the whole hover and no Simulation flag or setback
   happens.
6. Control: run the same steps while sneaking, or standing on a
   `#suppresses_bounce` block. Grim zeroes Y (sneak path) and the modified
   client should flag, which confirms the gap is only on the bounciness path.

### Fix direction

On 26.2+ clients, only skip the bounce when `currentY >= 0` for block
restitution (slime/bed `bounceUp`). For entity bounciness, call
`getVelocityAfterVerticalCollision` for both signs, or set Y to 0 on ceiling
hits, whichever the 26.2 client does. Confirm against
`Entity#move` / `Block#updateEntityMovementAfterFallOn` in 26.2.

## 2. Bounce window on a ground-status toggle lets the player pick their bounce

### Where

`predictionengine/predictions/PredictionEngine.java` (`handleStartingVelocityUncertainty`):

```java
if (player.uncertaintyHandler.onGroundUncertain && vector.vector.getY() < 0
        && !player.uncertaintyHandler.influencedByBouncyBlock()) {
    double movementY = Math.max(minVector.getY(), -player.getMovementThreshold());
    double bounceY = BlockProperties.getVelocityAfterVerticalCollision(player, minVector.getY(), movementY);
    if (bounceY < 0) minVector.setY(bounceY);
    else             maxVector.setY(bounceY);
}
```

`onGroundUncertain` is set in `events/packets/CheckManagerListener.java` when
the client sends a ground-only flying packet that flips `onGround` while
within 0.03 of the ground.

### Why it is a bypass

- Before 26.2 the bounce helper always returned 0 here, so this block only let
  the player cancel Y to 0 (a 0.03 landing).
- With entity `bounciness` > 0 it returns a positive `bounceY`, and the code
  sets `maxVector.y = bounceY` while keeping `minVector.y` at the falling
  velocity. The allowed range becomes the whole interval
  `[falling velocity − 0.03…, bounceY]`, so the client can choose any vertical
  velocity in it. Vanilla only allows exactly one value: the bounce if the
  player touched the ground, or the fall if they did not.
- `bounceY` is computed from `minVector.y`, which already includes the
  `−0.03` from `getVerticalOffset` (onGroundUncertain) plus any other negative
  uncertainty. The bounce is therefore up to `≈ 0.03 · 0.98 · bounciness`
  stronger than the real impact speed allows.
- `influencedByBouncyBlock()` only looks at slime, beds, honey and shelf
  mushroom. Entity bounciness is not included, so this branch is not
  suppressed for bouncy players.

Consequences:

- **Energy injection.** Every toggle-bounce adds up to about 0.03 m/tick of
  upward speed. A vanilla bounce with `bounciness = 1` loses about
  `1 − 0.98^(2t)` per cycle to drag and stops once `|v| < gravity`. With the
  extra 0.03 per bounce, a small bounce (`|v|` around 0.1–0.2) gains more than
  it loses, so the player can keep bouncing forever instead of settling. A
  vanilla client cannot do this.
- **Bounce on demand / partial bounce.** The client can start a bounce of any
  size from `0` to `bounceY` without touching the ground (only within 0.03 of
  it), and pick heights that vanilla would not allow on that tick.

### Reproduction

1. `/attribute @s minecraft:bounciness base set 1.0` and stand on flat stone
   (not on any `#suppresses_bounce` block).
2. Vanilla baseline: jump off a 3-block pillar with an unmodified client. The
   bounces shrink and stop after a few cycles. Record the Y apex of each bounce
   with `/grim debug`.
3. Test client: on the tick where the client is falling and its feet are 0 to
   0.03 above the floor, send a flying packet with no position, `onGround=true`
   (the flip that sets `onGroundUncertain`), and do not send the colliding
   position. On the next position packet, apply
   `y = (|v| + 0.03) * 0.98` (the top of Grim's range) instead of the vanilla
   bounce.
4. Repeat on every descent.
5. Expected: the apex stays the same or grows instead of shrinking, and the
   debug offset stays under the threshold the whole time. Start from a standstill
   with a small drop (around 0.5 blocks) to show that bouncing that vanilla
   would stop continues indefinitely.

### Fix direction

- Add entity bounciness (`getEntityBounciness(player) > 0`) to
  `influencedByBouncyBlock()`, or give it its own flag so it uses the existing
  slime-style uncertainty that limits the bounce to the tracked
  `nextTickSlimeBlockUncertainty`.
- Compute `bounceY` from the un-inflated `vector.vector.getY()` instead of
  `minVector.getY()`.
- Use two candidate Y values (fall or bounce) instead of the whole interval.

## 3. `air_drag_modifier` is not applied to elytra drag

### Where

- Ground, air and flying movement use the modified drag:
  `MovementTicker.livingEntityTravel` →
  `BlockProperties.getModifiedAirDrag(0.91F, player)`, and
  `PredictionEngineNormal.staticVectorEndOfTick` →
  `getModifiedAirDrag(0.98F, player)`.
- Elytra does not:
  `predictionengine/predictions/PredictionEngineElytra.java:107`

```java
result.vector.clone().multiply(0.99F, 0.98F, 0.99F)   // hard-coded, ignores AIR_DRAG_MODIFIER
```

  and `MovementTicker` sets `player.friction = 0.99F` for gliding.

### Why it is a bypass

`getModifiedAirDrag(d) = clamp(1 − (1 − d) · air_drag_modifier, 0, 1)`. With a
modifier above 1, vanilla drag is stronger:

| `air_drag_modifier` | horizontal drag (vanilla, if applied) | Grim elytra |
|---|---|---|
| 1.0 | 0.99 | 0.99 |
| 2.0 | 0.98 | 0.99 |
| 5.0 | 0.95 | 0.99 |
| 10.0 | 0.90 | 0.99 |

If 26.2 applies the modifier to the elytra drag constants, as it does to the
`0.91` and `0.98` constants Grim already handles, then a player with
`air_drag_modifier = 5` loses 5% of horizontal speed per tick in vanilla, while
Grim accepts the 1% loss of an unmodified glide. Over a 100-tick glide that
is about `0.99^100 / 0.95^100 ≈ 61×` more retained speed than vanilla allows,
which is an elytra speed boost on servers that use the modifier, for example
as a slowness/"heavy" effect.

The inverse (`air_drag_modifier` < 1) makes Grim stricter than vanilla and
causes false positives. That direction is not a bypass.

### Reproduction

1. Confirm in the 26.2 client sources whether `LivingEntity#travelFallFlying`
   (or its 26.2 equivalent) runs its drag constants through the air-drag
   modifier. If it does not, this finding is invalid.
2. `/attribute @s minecraft:air_drag_modifier base set 5.0`, equip an elytra,
   jump off a tall tower and glide at a fixed pitch of 0°.
3. Vanilla baseline: record horizontal speed per tick with `/grim debug`.
   Expect it to decay faster than without the modifier.
4. Test client: force the elytra drag back to `0.99/0.98/0.99` (ignore the
   modifier).
5. Expected: Grim reports offset ≈ 0 for the modified client and flags (or
   shows an offset for) the vanilla client.

### Fix direction

Apply `getModifiedAirDrag` to the elytra drag constants (and to
`player.friction` and the `0.99` in `UncertaintyHandler`'s gliding 0.03
estimate) for 26.2+ clients. Check vehicle paths that hard-code `0.91` or
`0.98` at the same time (boats `PredictionEngineBoat`, `addNonEffectiveAI`,
`lastDummy` in `MovementCheckRunner`).

## 4. Cube-mob size metadata index on 26.2 servers (verification item)

### Where

`utils/latency/CompensatedEntities.java`:

```java
} else {
    // 26.2 cube mobs have different index (phantoms and others still retain old index)
    final boolean cubeMob = type == SLIME || type == MAGMA_CUBE || type == SULFUR_CUBE;
    id = cubeMob ? 18 : 16;
}
EntityData<?> sizeObject = WatchableIndexUtil.getIndex(watchableObjects, id);
if (value instanceof Integer) sizeable.size = (int) value;
```

`BoundingBoxSize` then uses `0.52 · size` (slime/magma) or `0.49 · size`
(sulfur cube) for width and height. Reach and Hitboxes use these boxes.

### Why it matters

The size is read from whatever **Integer** sits at index 18. If the 26.2
layout for any of the three types (most likely `SULFUR_CUBE`, which has extra
state such as the absorbed block) has another integer field at 18, Grim will
store that value as the size:

- A large unrelated integer gives a very large hitbox. Reach and Hitboxes
  would then accept hits far outside the real slime/sulfur cube box. This is
  a reach bypass against that mob type, and a hit-through-cube bypass against
  players standing behind or inside it, since the Reach ray hits the cube.
- If the field is missing, `size` stays at its default of `1`. That only makes
  Grim stricter (false positives).

### Reproduction / verification

1. On a 26.2 server, `/summon minecraft:sulfur_cube ~ ~ ~ {Size:0}` and
   `{Size:3}`, and the same for slime and magma cube.
2. Log the metadata packet (packetevents debug or a small listener) and check
   that index 18 is the size `VarInt` for all three types and that no other
   `Integer` sits at 18.
3. If any type differs, attack that mob from about 3.2 blocks away against the
   edge of its real box, using a client that sends the attack without the
   vanilla range check. Grim should flag Reach. If it does not, the hitbox is
   inflated.

### Fix direction

Index per type from the 26.2 `EntityDataSerializers` layout, and check the
serializer type (size is a `VarInt`) before trusting the value.

## Checked and not counted as bypasses

These were reviewed and look either faithful to vanilla or only stricter:

- **Geyser launch (`PotentSulfurGeyser`)**: applied every time, with no
  "maybe" branch, so a client cannot choose to take or skip the push. The
  search window (`floor(minY) − 25 … floor(maxY) − 1`), the 6-blocks-per-water
  force height, the `0.3 + 0.1·water` cap and the tick order all look
  internally consistent. Excluding spectators, creative-flying players and
  the ender dragon matches the tag. Geyser state changes go through the
  transaction-compensated world (`CompensatedWorld.updateBlock` →
  `CompensatedGeysers.updateBlock`), and chunk loads and unloads go through
  `addRealTimeTask`.
- **Swim-hop + geyser** (`GrimPlayer#getPossibleVelocitiesMinusKnockback`):
  Grim's relaxed `canSwimHop` (no `isFree` check, as its own comment says) is
  a pre-26.2 leniency. Applying the geyser to the swim-hop vector gives at most
  `0.3 + 0.2 = 0.5`, which does not exceed the geyser's own cap, so 26.2 does
  not make it worse.
- **`getFrictionInfluencedSpeed` `≤ 0.6` short-circuit**: at friction 0.6
  the old formula gives `0.21600002/0.216 ≈ 1.0000001`, so the two match. For
  friction lowered below 0.6 by `friction_modifier`, the short-circuit caps
  speed, which is the purpose of the 26.2 change.
- **26.2 baby-mob hitbox changes (hoglin, zoglin, fox, goat, camel)**:
  every type that gets `getBabyScaleFactor == 1` on 26.2
  also has an explicit 26.2 baby width **and** height, so no baby is left with
  an adult-sized box.

## Not bypasses (false-positive risks found along the way)

- Entity bounciness is missing from `influencedByBouncyBlock()` and the
  PointThree bouncy-block uncertainty, so legit bouncy players lose the hidden
  0.03 bounce allowance. This is the same root cause as finding 2. Fix them
  together.
- `STRAW_BED` bounces (0.75) for 26.2 clients in `getBlockBounceRestitution`,
  but `MovementCheckRunner` only marks `BlockTags.BEDS` as a bouncy block. If
  straw bed is not in that tag, its uncertainty is missing.
- The PointThree / 0.03 constants in `UncertaintyHandler` assume 0.91 air drag
  and at most 0.989 friction. `air_drag_modifier < 1` or
  `friction_modifier < 1` can push the real values to 1.0.
- Ceiling hits with bounciness (finding 1) also cause false positives for
  legit 26.2 clients, which do bounce off the ceiling.
